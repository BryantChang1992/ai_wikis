# 知识库维护流程

2026-10-09 修订。规范以仓库 `AGENTS.md`、`知识库/schema.md` 为准；本页是可执行操作入口。过去引用的外置 shell scripts 和 reference 模板不在本仓库，不能假设已安装或声称运行过。

## 1. 进入与选择范围

定位实际 checkout 根目录，不硬编码工作路径。先读 purpose、schema、README、缺口表与最近日志。确认本次是 ingest、query、lint 或 synthesize，阅读相关完整文件，记录当前分支、HEAD、远端和未提交改动。不得顺带改团队 Agent 核心文件或定时任务。

## 2. 摄取与关联更新

核对来源身份、版本、版权和取得状态，按 DOI/URL/哈希去重。原文保留，派生分析单独标识。优先修订既有页；不以固定数量、字数或模型分数拆卡。更新受到新证据影响的概念、实体、专题和综述，记录每个关联的理由，避免仅为消除孤儿而添加无意义链接。

遇到来源错配、版本混用或冲突，核对证据并修正文内断言；暂时无法判断则同时保留证据，记入缺口表。缺失页面应判断是否值得研究，不直接删掉语义问题，也不制造空壳。按 schema 的精读门槛区分原文核读、摘要阅读、未取得和未复现。

## 3. 查询与综合

先用总索引定位，再读关联页与原始证据。回答附出处和适用条件。授权范围内把可复用的比较、纠错或新联系回写既有页，必要时才建新页。对新材料检查综述是否需要变化，不按 5 页、2 类型或每页一图机械执行。无增量则记录原因。

## 4. 校验与记录

仓库根运行：

```sh
python3 -m unittest discover -s scripts -p 'test_*.py'
python3 scripts/maintain_wiki.py --root .
python3 scripts/maintain_wiki.py --root . --check
```

公开产物真实复用既有页时先按 [[知识库/动态管理规则]] 记录 use；审阅通过的 lifecycle 变化用 decision，撤销用 restore。上面的维护入口会实际重建重要性排序与候选，追加变化记录，保留正文和原始资料。它不依赖后台调度。

另外人工/LLM 审阅证据、矛盾、版本和知识缺口。结构通过不能表示语义全部正确。新报告写入 `知识库/维护记录/`，保留历史报告。只在实际核读后更新 source_checked；不统一更新旧页日期或 confidence。

核对来源索引、README、真实双向引用和相关综述。在同一次提交前向 `知识库/log.md` 追加操作、影响页、验证范围和未解决事项。

## 5. 安全提交与同步

先检查 `git status --short`、当前分支及完整 diff。只 `git add -- <明确路径...>`，避免混入其他任务改动。远端有新提交时先检查分歧和冲突，保留双方修改；不可盲目覆盖或 force push。检查后提交，推送并重新读取远端 head 及文件。

双端发布仅处理本次授权技术内容。已有博客清单及哈希不因导航/规范修改而伪造刷新。用户要求仅入 vault 的专题不自动发博客。桌面同步按 `知识库/维护记录/Obsidian与GitHub同步操作.md`，不能把云端快照当成用户桌面 vault。

## 完成标准

- 来源及派生角色清楚，未取得的证据明确列出。
- 相关页、综述、索引与日志同步完成，未解冲突进入缺口表。
- 结构检查和针对性语义审阅有记录，未跑测试不冒称通过。
- 只提交本次文件，原始资料和用户修改未丢失；远端读回已核实。
- 桌面同步已验证或明确待验证，不把两者混为一谈。
