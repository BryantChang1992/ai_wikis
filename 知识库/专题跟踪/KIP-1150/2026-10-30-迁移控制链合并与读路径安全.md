# KIP-1150 周记：迁移控制链合并，读路径安全仍待闭环

观察区间：**2026-10-23 12:00 至 2026-10-30 12:00 UTC**，衔接上期事件截止点。实际检索截止见文末；截止后的事件不倒填为本周成果。

本周的主要变化不在 ASF 提案状态，而在独立 fork Inkless 的工程实现：**控制器两阶段规则与 broker 上传确认发起端已经合并，但 flag 生效后的读路径、consolidation 和 ISR 收缩仍在评审。**因此，不能把“能提交迁移标记”写成“迁移正确性已全链路交付”，更不能把 fork 的合并写成 Apache Kafka 发布。背景参见[[知识库/专题跟踪/KIP-1150/2026-10-09-从起点到现在|首篇]]；上期问题参见[[知识库/专题跟踪/KIP-1150/2026-10-23-提案状态未变与迁移实现推进|10 月 23 日周记]]。

## 2. 从控制器规则到上传确认：上期开放的两项实现已合并

### 控制器已经按耐久责任切换规则

[#833](https://github.com/aiven/inkless/pull/833)于 **10 月 23 日 13:53:35 UTC** 合并，属于本期，而不是上期。phase 1 的 classic prefix 仍只由本地 ISR 副本完整持有，所以选主必须检查在线日志目录，重分配仍走 adding/removing 的分阶段路径，broker unfence 不能直接把缺旧数据的副本加入 ISR。`classicPrefixInRemoteStorage=true` 后才采用 born-diskless 的宽松规则。[固定合并](https://github.com/aiven/inkless/commit/27b691d570945fd5d88918396715d13731b72ef3)

该变更也拒绝 phase 2 的任何 seal 调整，连调低、设成同值都不允许：此后本地旧前缀可能被删除，consolidation 从已承诺边界继续，不能再让管理员修改过去的责任分界。重分配被重新指定目标时，还要处理旧的 adding/removing 集合，不能因“新目标等于当前副本”就保留一个永远完不了的旧移动。这是控制器规则的闭合，不等于 broker 侧已经遵循所有阶段规则。

### broker 终于能把“旧前缀已上传”送给控制器

[#835](https://github.com/aiven/inkless/pull/835)于 **10 月 29 日 14:43:34 UTC** 合并。上期已描述的 WaitingForUpload → SendingFlagToController 现在进入主分支：leader 检测 `highestOffsetInRemoteStorage >= seal - 1`，或旧前缀已被 retention / DeleteRecords 移除、`logStartOffset >= seal`，然后批量发起 SetClassicPrefixInRemoteStorage。活跃 segment 若仍包含前缀尾部，需要先 roll，否则空闲 topic 可能永远等不到远端管理器上传。[合并版迁移说明](https://github.com/aiven/inkless/blob/6ef58bd1e52feab920b86d86a8f1f0748d7d22e2/docs/inkless/CLASSIC_TO_DISKLESS_SWITCH.md)

本周新增的关键评审不是再列一次状态名，而是**旧请求失败不能删除新状态**：原 InitDisklessLog 的响应丢失后，seal 可能已通过 KRaft 被 broker 看见，上传观察状态也已建立；旧请求的重试再被控制器拒绝，如果按 partition 无条件 remove，就会清掉新的 WaitingForUpload，使它只能等下一次选主才重启。最终补丁用对象引用确认槽内仍是发起请求的那一代状态，再删除，并取消被替代的旧队列请求。相同 payload 也可能是不同代，所以不能只比较值。[反例与建议](https://github.com/aiven/inkless/pull/835#discussion_r4413016918) · [取消旧重试的配套要求](https://github.com/aiven/inkless/pull/835#discussion_r4413273190) · [已合并实现](https://github.com/aiven/inkless/blob/6ef58bd1e52feab920b86d86a8f1f0748d7d22e2/core/src/main/scala/kafka/server/InitDisklessLogManager.scala)

评审还纠正了 epoch 示例：Kafka metadata version 3.6 以后，单纯 ISR shrink 不一定推进 leader epoch；删除副本的重分配可以保持同一个 leader 而推进 epoch。因此重试必须读取当前 epoch，不能因为 leader 身份未变就重发旧 epoch。[评审原文](https://github.com/aiven/inkless/pull/835#discussion_r4412964034)

监控也分开了“初始化完成”与“迁移上传完成”：既有 InFlightPartitions 不包含新等待阶段，降至零不能证明 phase 2 已到达；新增等待数量、最老等待年龄、flag RPC 成败及重试指标才用于定位卡点。上述测试为提交者报告和代码核读结果，本次没有运行集群复现。

## 3. 标记提交之后，真正可读仍是下一道门

### #840 仍开放：远端存在不等于每个副本都能正确读

10 月 28 日打开的 [#840](https://github.com/aiven/inkless/pull/840)补齐 broker 的 phase gating，截止仍未合并。phase 1 禁止 consolidation 推进跨层起点，客户端只路由到存活 ISR；phase 2 则删除本地旧前缀、从远端读取，并开始 consolidation。原因是 phase 2 控制器可能接纳并无可信本地旧数据的副本，不能继续相信任意本地 prefix。

10 月 29 日评审指出，删除旧前缀并不自动让远端读取安全：follower 的 remote log metadata 可能尚未消费上传完成记录，远端对象确实存在，但本 broker 查不到覆盖区间，返回 OOR 后消费者可能 reset、跳过仍应保留的数据。另有副本 LEO 已等于 seal、但 classic epoch cache 分叉的情形；错误 epoch 会让远端 segment 定位失败。[远端元数据落后](https://github.com/aiven/inkless/pull/840#discussion_r4413966568) · [epoch 历史问题](https://github.com/aiven/inkless/pull/840#discussion_r4413966501)

截止前候选文档已把删除限制为**本 broker 已知远端覆盖的 segment**，不足时周期重试，phase 2 中尚存的本地前缀读返回可重试的 NOT_LEADER_OR_FOLLOWER；不能仅凭全局 flag 就把暂时不可见误判成过期。对 epoch 分叉问题，本期核读了评审意见，但不将其视为已经得到独立验证的完整闭环。

10 月 30 日 11:39 UTC 又出现日志目录迁移竞态：fetch 已通过旧 current log 的 guard，future log 随后被提升，却还带着未验证旧前缀；若提升后才清理，窗口内仍可读到错误本地数据。评审同时指出提升路径持有 partitionMapLock 再进入 markPartitionOffline，可能与日志目录失败处理发生锁序反转。作者 11:46 的回复与候选补丁把清理放到 future log 提升前，必要时延迟提升，并移除提升后的 offline 回调。**这是评审中的修订和作者回应，不是已合并或已发布保证。**[读竞态](https://github.com/aiven/inkless/pull/840#discussion_r4423197657) · [锁序反转](https://github.com/aiven/inkless/pull/840#discussion_r4423197732) · [修订回应](https://github.com/aiven/inkless/pull/840#discussion_r4423255410)

候选仍声明：跨过 seal 的旧 segment 不能整体删除；remote storage 关闭或 copy disabled 时旧前缀保留但读取失败。DeleteRecords、RetentionEnforcer 等也不在本 PR 的完整解决范围。应继续盯住跨组件交错测试，而不是仅统计新增单测个数。

### #841 仍开放：ISR 收缩也要按阶段判断

同日打开的 [#841](https://github.com/aiven/inkless/pull/841)依赖 #840。旧实现跳过所有 diskless topic 的 maybeShrinkIsr，但 phase 1 的本地副本仍承担唯一完整旧前缀的耐久责任，停止 fetch 的副本不能一直保持可选主资格。候选仅对 phase 1 恢复 classic 收缩规则，born-diskless 与 phase 2 保持跳过。

与此同时，新 leader 必须重新得到 follower 的 fetch 状态：当 consolidation 未启用、follower 已停在 seal 时，需要在新 epoch 至少安排一次 fetch，否则新 leader 可能在 lag timeout 后误删正常副本。作者报告该栈系统测试 37 通过、1 忽略，但这不是本次复现，也不是独立的 ASF 验收；截止仍 open，不能写成迁移已全面安全。

## 4. 控制平面错误分类与后台回收，显示另一组工程边界

[#839](https://github.com/aiven/inkless/pull/839)于 **10 月 30 日 11:34:24 UTC** 合并。控制平面不可用时，CreateTopics / DeleteTopics / CreatePartitions 不再把整批 topic 统一变成无信息 UNKNOWN_SERVER_ERROR，而只对受影响 diskless topic 返回可重试 KAFKA_STORAGE_ERROR，并保留原因。CreateTopics 的既有 topic 重试需要从 metadata image 补齐 ID、分区数等信息，才能补写缺少的控制平面行。

但“可重试”不等于跨存储原子事务：删除先改控制平面、再改 KRaft，若第二步失败而客户端不再重试，后台清理可能移走数据，KRaft 却仍留着 topic；随后同名 CreateTopics 得到 TOPIC_ALREADY_EXISTS，修复路径会以同一 topic ID 重建空行。维护者要求文档明确持续重试删除及日志追踪，此风险已进入合并版说明，而不是被 PR 消除。[评审风险](https://github.com/aiven/inkless/pull/839#discussion_r4399226466) · [固定版 FEATURES](https://github.com/aiven/inkless/blob/63cc8f0814839afb88fafc10c6410f04ac817223/docs/inkless/FEATURES.md)

[#843](https://github.com/aiven/inkless/pull/843)于 10 月 28 日提出，截止 open。它把已 tiered WAL 的一次无界大删除拆为每 partition 独立重试、每次最多默认 2000 个 batch，保留旧 SQL function 以兼容滚动升级/回滚。因为 prune 与 produce commit 竞争同一 logs 行锁，优化目标是缩短最长持锁时间，而不是最小化总清理耗时。作者的本地固定数据集显示总时长增加、最大阻塞降低；这只是作者基准，不能推导生产吞吐或通用倍数保证。10 月 30 日评审继续要求错误率指标，尚未完成合并。

新开的 [#846](https://github.com/aiven/inkless/pull/846)则处理布尔配置解析不一致：KRaft 接受 True/TRUE，但控制平面注册只比较小写 true，会留下“元数据认为 diskless、控制平面无行”的 topic。截止仍 open，测试通过数字为作者报告。这说明双平面一致性不仅取决于故障恢复，也取决于入口配置语义统一。

## 5. 发布与上游核验：不能沿用上期的版本清单

Inkless 最新可见 release 仍是 [0.50（10 月 19 日）](https://github.com/aiven/inkless/releases/tag/inkless-release-0.50)。#833/#834/#835/#839 均晚于该发布日期，本次没有发现包含这些本周合并的新 fork release。上期 #834 的截止后合并现在应记入本期：**10 月 23 日 12:42:57 UTC**，主要是 untiered diskless 迁移的文档和测试，不新增 broker 生产逻辑。它保留 RF 1 路由、短 retention 的配置约束，不能概括为任意 topic 无条件在线迁移。[#834](https://github.com/aiven/inkless/pull/834)

Apache 的[下载页](https://kafka.apache.org/community/downloads/)当前列出 4.4.0（10 月 22 日）与 4.3.2（10 月 23 日）。本期补核 [4.4.0](https://dlcdn.apache.org/kafka/4.4.0/RELEASE_NOTES.html)及 [4.3.2](https://dlcdn.apache.org/kafka/4.3.2/RELEASE_NOTES.html)发布说明，未检出 Diskless 或 KAFKA-19161。上期仅列旧版本的核验不能当作本期完整发布目录；发布日期也不是所有内容已在上期检索时核实的证明。

截止前上游快照为 [30febe13](https://github.com/apache/kafka/commit/30febe135f895cf5f3b418b673abb844ad059bc1)。六份 schema 定点检查延续上期：MetadataRequest 与 DescribeTopicPartitionsRequest 仍无 RackId，AlterPartitionRequest / PartitionRecord / PartitionChangeRecord 仍无 StorageEngines，FindCoordinatorRequest 仍无 DISKLESS 类型。[客户端协议目录](https://github.com/apache/kafka/tree/30febe135f895cf5f3b418b673abb844ad059bc1/clients/src/main/resources/common/message) · [元数据协议目录](https://github.com/apache/kafka/tree/30febe135f895cf5f3b418b673abb844ad059bc1/metadata/src/main/resources/common/metadata)

结合提案、issue、固定源码与发布说明，本期仍无可确认的 Apache Kafka 完整 Diskless 正式交付。六个文件和关键词搜索不是所有实现分支的穷尽审计，不能推出“任何代码都没写”。
