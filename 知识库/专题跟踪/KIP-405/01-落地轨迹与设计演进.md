# KIP-405：从提案到可用实现的落地轨迹

核验日期：2026-10-09。范围：Apache Kafka 上游；不把厂商自有 Tiered Storage、内部原型分支或未发布的 trunk 当作 Apache Kafka 已发布能力。PR 日期均为 GitHub 的 `merged_at` UTC 日期；JIRA 的 Fix Version 用于辅助判断进入哪个发行版，最终发布状态以官方发行说明为准。

## 一、最重要的结论

KIP-405 不是“一次合并、一个版本完成”的改造：2019 年有端到端草案 PR，2021 年开始按组件陆续合并，2023 年 Kafka 3.6.0 首次以 Early Access 对外发布，2024 年 Kafka 3.9.0 才被官方宣布 production-ready。生产就绪之后仍继续完善读取并发、线程池和 follower bootstrap。

两个关键官方里程碑已经直接核验：

- **3.6.0，2023-10-10：Early Access，只建议非生产环境测试。** [3.6.0 官方公告](https://kafka.apache.org/blog/2023/10/10/apache-kafka-3.6.0-release-announcement/)
- **3.9.0，2024-11-06：production-ready。** 同次发布包含按 topic 禁用、传输配额、远端相关 offset 查询及 dump-log 支持。[3.9.0 官方公告](https://kafka.apache.org/blog/2024/11/06/apache-kafka-3.9.0-release-announcement/)

截至核验日，官方下载页最高发布分支为 4.3，最高版本为 4.3.1（2026-06-25）。4.2.2 在 2026-09-29 发布，但它是较低维护分支的新补丁，不能混称“最高 Kafka 版本”。[官方下载页](https://kafka.apache.org/community/downloads/)

## 背景：为什么不能只给 broker 加更大的盘

经典 Kafka 把每个分区的日志存放在 broker 本地，并由 follower 复制。实时消费者主要追日志尾部，热数据可以命中 page cache；回填、追溯或重放才会访问很久以前的段。这两类访问的频率、延迟要求和容量需求不同，却一起占用 broker 的本地存储与副本容量。

长期保留增大后，扩容不只取决于 CPU 和实时吞吐，还可能受磁盘容量驱动；新 broker 接管副本时，历史搬运也会消耗网络与恢复时间。KIP-405 的选择是保持热路径，给关闭的稳定段增加共享远端层。broker 留一段较短的热窗口，历史段及相关恢复信息放入更适合长期容量的系统，消费者仍使用既有 Kafka 协议。[原提案 Motivation / Proposed Changes](https://cwiki.apache.org/confluence/spaces/KAFKA/pages/97554472/KIP-405+Kafka+Tiered+Storage)

这项优化的目标是**把历史容量与实时服务资源适度解耦**，而不是承诺 broker 无状态，也不是把 producer 的成功响应改成等待对象存储上传。活跃段仍在本地，复制协议仍保护热数据；跨 AZ 热复制成本也不会自动消失。因此它与 [[知识库/专题跟踪/KIP-1150/README|KIP-1150 Diskless]] 的问题边界不同。

### 工程挑战怎样变成了设计结构

| 挑战 | 如果只“上传文件”会怎样 | KIP-405 的解决方向 |
|---|---|---|
| 数据和目录无法一次原子提交 | 半份对象被列为可读；上传完成但元数据未成功时状态不确定 | 独立 RSM / RLMM；COPY_STARTED → COPY_FINISHED 状态机；以元数据确认推进 |
| leader 更替及日志历史分叉 | 同一个 offset 可能对应不同历史，旧 leader 的段混入新历史 | topic 身份、segment UUID、leader epoch 范围参与定位与恢复 |
| 删除本地历史后如何查找 | 只保留日志 payload，offset/time 查询、事务过滤和生产者恢复缺辅助信息 | 一同保存 offset/time/transaction index、producer snapshot、leader epoch checkpoint |
| 远端延迟与本地请求处理不同 | 冷读取占普通请求线程，拖慢其他分区 | 专门远端读执行器、异步结果与 delayed fetch；后续再放开多分区并发 |
| 全局保留与本地容量不同 | 本地到期就删，尚未上传时可能丢历史；或远端永久不清理 | 区分 logical log start 与 local log start；本地回收与远端删除各有进度和策略 |
| 换 broker 不想搬全部冷历史 | 恢复要么过慢，要么少了 epoch/producer 状态 | 先恢复远端辅助状态，再复制必要热尾部；4.3 继续优化起点 |
| 存储系统差异很大 | 核心硬编码每家对象存储的认证/请求/布局 | SPI 插件边界；核心提供生命周期机制，生产 RSM 由独立实现承担 |

表中是贯穿最终实现的因果解释；具体方法、状态前置条件和异常路径见[[知识库/专题跟踪/KIP-405/02-核心代码与关键交互流程|源码篇]]。其中“两个阶段”是应用层可恢复状态流程，**不是对象存储与 Kafka 元数据 topic 组成了 XA/两阶段提交事务**。

## 四、3.9 GA 后围绕 KIP-405 的直接演进

### 3.9：从基础能力到可运维

3.9 官方公告明确列出：KIP-950 提供 topic 级禁用；KIP-956 提供上传/下载速率配额；KIP-1005 暴露 earliest-local / latest-tiered offset 能力；KIP-1057 让 dump-log 工具能够解析远端日志元数据记录。[3.9 官方公告](https://kafka.apache.org/blog/2024/11/06/apache-kafka-3.9.0-release-announcement/)

禁用有两种实质不同的操作：保留 `remote.storage.enable=true` 并设置 `remote.log.copy.disable=true`，停止新上传但仍可读历史远端数据；或者设置 `remote.storage.enable=false,remote.log.delete.on.disable=true`，禁用并删除远端数据。只读模式还需把 local retention 调整为继承总 retention（`-2`）或与其相同。[KIP-950](https://cwiki.apache.org/confluence/spaces/KAFKA/pages/263424654/KIP-950+Tiered+Storage+Disablement)

KIP-950 曾同时设计 ZK/KRaft 流程，但提案中的“计划支持”不能视作实际发布范围。实际 #16653 明确禁止在 ZK 下启用这些禁用配置；GA notes 也强调 topic 级切换能力属于 KRaft。因而适合写“3.9 引入 KRaft topic 级 disable/re-enable”，不适合写“3.9 所有模式都可以”。[#16653](https://github.com/apache/kafka/pull/16653)、[GA notes](https://cwiki.apache.org/confluence/spaces/KAFKA/pages/315494647/Kafka+Tiered+Storage+GA+Release+Notes)

### 4.0：线程池独立配置

copier 和 expiration 池默认值由 `-1`（继承旧池配置）改为 `10`，最小值改为 `1`；旧 `remote.log.manager.thread.pool.size` 的默认值由 `10` 改为 `2`，其剩余工作主要是轻量 follower 任务。显式遗留 `-1` 的配置在升级时需修改。[KIP-1030](https://cwiki.apache.org/confluence/spaces/KAFKA/pages/296290836/KIP-1030+Change+constraints+and+default+values+for+various+configurations)

### 4.2：远端读取并发化

KAFKA-14915 / #20045 打破了“一个 Fetch 请求只能读取一个远端分区”的限制。与之相关的 KAFKA-19763 内存泄漏和 KAFKA-19795 响应体积控制修复，也列入 4.2.0 发行说明。因此，2025 年 GA notes 中那条单分区读取限制只能用于描述较早版本。[KAFKA-14915](https://issues.apache.org/jira/browse/KAFKA-14915)、[#20045](https://github.com/apache/kafka/pull/20045)、[4.2.0 发行说明](https://archive.apache.org/dist/kafka/4.2.0/RELEASE_NOTES.html)

4.2 同时弃用名称不够明确的 `remote.log.manager.thread.pool.size`，改用 `remote.log.manager.follower.thread.pool.size`。[升级文档](https://kafka.apache.org/43/getting-started/upgrade/)

### 4.3：新 follower 可以跳过已经上传的本地段

原 KIP-405 选择从 leader 的 earliest local offset 复制，保留对本地 retention 的一致性。KIP-1023 则增加可选优化：`follower.fetch.last.tiered.offset.enable` 默认 `false`；打开后，新加入且本地日志末端为 0（LEO=0）的 follower 可以从 earliest pending upload offset 开始，仅复制尚未上传的数据，并先建立对应辅助状态。它没有把 follower 正常复制方式整体替换成“直接从对象存储拉全量”。[4.3.0 公告](https://kafka.apache.org/blog/2026/05/22/apache-kafka-4.3.0-release-announcement/)、[#20428](https://github.com/apache/kafka/pull/20428)

4.3 还增加 `remote.log.metadata.topic.min.isr`（默认 `2`，KIP-1235）及 `remote.log.metadata.admin.` 独立 AdminClient 配置前缀（KIP-1208），继续加强默认 RLMM 的可靠性与可配置性。既有元数据 topic 的 min.insync.replicas 需按升级说明自行核对。[4.3 升级说明](https://kafka.apache.org/43/getting-started/upgrade/)

## 五、原 KIP、GA notes 与 4.3 当前文档的差异

| 议题 | 早期材料可能让人得到的印象 | 截至 4.3 的准确说法 |
|---|---|---|
| JBOD | KIP-405 Non-Goals / Limitations 写“不支持” | 已在 3.8.0 支持；3.9 GA 也确认支持。 |
| topic 禁用 | KIP-405 写“一旦启用不可禁用” | 3.9 KRaft 增加停止复制、禁用并删远端、再次启用。 |
| 一次 Fetch 多远端分区 | GA notes 写“最多一个” | KAFKA-14915 已在 4.2.0 修复；引用 GA notes 时必须附版本。 |
| follower bootstrap 起点 | KIP-405 选择 earliest local offset | 4.3 增加默认关闭的 last-tiered-offset 优化；不开时仍保留原有路径。 |
| RLM 线程池名称和默认值 | 老文章可能只列一个 10 线程池 | 3.9 拆池，4.0 修改默认值，4.2 重命名 follower 池；不要混列成同一版本配置。 |
| 开箱即用 S3/HDFS 插件 | 看到提案举例或草案代码，误认为 Apache Kafka 自带 | 4.3 官方文档仍明确没有开箱即用的 RSM 实现；生产需要配置适配器。`LocalTieredStorage` 是测试模拟。 |
| compacted topic | 原 KIP 不支持 | 4.3 官方文档仍不支持。KIP-1272 页面仍为 Under Discussion，不能当成已发布能力。 |
| 缺 producer snapshot 的老段 | 升级后可无条件直接启用 | 4.3 文档仍列缺 snapshot 不支持；重点检查源自 2.8.0 之前的段。 |

本表对应证据：前三项分别见 [3.8 公告](https://kafka.apache.org/blog/2024/07/29/apache-kafka-3.8.0-release-announcement/)、[#16653](https://github.com/apache/kafka/pull/16653)、[KAFKA-14915](https://issues.apache.org/jira/browse/KAFKA-14915)；当前插件与限制见 [4.3 Tiered Storage 文档](https://kafka.apache.org/43/operations/tiered-storage/)；compaction 的未来方案见 [KIP-1272](https://cwiki.apache.org/confluence/spaces/KAFKA/pages/406618989/KIP-1272+Support+compacted+topic+in+tiered+storage)。

### 文档本身也有需要谨慎处理的地方

- KIP-405 页眉已补“3.9 production-ready”，正文还保留早期限制与 future work，不能视为某个 release tag 的完整规范。
- 4.3 操作文档的禁用示例段仍说关闭 broker 远端功能前要删除 topic，而其 Limitations 说要先禁用所有相关 topic。写实际操作手册时，宜以目标 tag 的配置校验和测试为准，不把较老示例变成“必须删业务 topic”的建议。
- 早期文档把 S3 一致性当作元数据层分离的历史动机之一。不要未经另外核验就转写成“现在 S3 必然是最终一致”；本研究只把它视作设计当时的讨论背景。
