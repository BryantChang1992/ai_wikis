## 2. 同一个 seal 不够：已合并的历史校验与远端读截断

上期仍在评审的 [Inkless #857](https://github.com/aiven/inkless/pull/857) 于 **11 月 11 日 13:26:25 UTC** 合并。它不是新的 Apache KIP 决策，而是独立 fork 的迁移恢复实现。核心问题不变：两个副本都到达 seal，并不表示 seal 前保存的是同一段历史。分叉副本可能带着旧 epoch cache、目录迁移中的 future log 和过高的远端上传进度回来；只把记录 truncate 到 seal，仍可能让清理器依据错误进度删除尚未安全分层的 WAL。

最终实现用 phase 2 flag 携带的 `lastClassicLeaderEpoch` 校验前缀，失败时停止相关 fetcher、删除 current/future log 并重新创建副本，保留远端元数据订阅后从远端重建。删除或取消任务失败就维持副本 offline，不能把部分重置当成功。重建定位 `seal - 1` 所属的记录历史，并从 seal 接续 diskless 数据，而不采用源副本任意的本地起点。[合并提交](https://github.com/aiven/inkless/commit/8ac5704ac8ac86be1c8f602b9a1383d94878df60)

相对上期，两个细节真正改变了候选的安全边界：

- **11 月 6 日 12:29 的自动评审**指出，读取新的 truncation count 但同时看到旧 epoch/cache，仍会放行旧远端进度。作者在 13:12 回应并修改为在日志锁内读计数；截断计数增加和日志状态改变也在同一锁内，补了暂停截断的回归测试。这里是已核读的代码与作者测试说明，不是本次独立故障复现。[质疑与回应](https://github.com/aiven/inkless/pull/857#discussion_r4492411539) · [修订说明](https://github.com/aiven/inkless/pull/857#discussion_r4492767751)
- **11 月 10–11 日人工评审**补上 future log 已完全落在当前 log start 之前的情况：这些数据已经不属于当前日志保留范围，不能仅因找不到旧 epoch 就重建健康副本。最终允许该情形通过，减少不必要重建，而非放宽仍存活数据的历史一致性检查。[评审](https://github.com/aiven/inkless/pull/857#discussion_r4526292204) · [修订与测试](https://github.com/aiven/inkless/pull/857#discussion_r4537318434)

### 修复恢复位置，还要限制一次读取的终点

上期明确留下的“远端 segment 跨过 seal”漏洞，本周由 [#867](https://github.com/aiven/inkless/pull/867) 于 **11 月 12 日 09:25:26 UTC** 合并处理。假如迁移前一次非干净选主丢掉了 `[100,120)`，远端却还存有覆盖 `[50,119]` 的旧 segment，而新 seal 是 100，消费者从 60 开始的远端读取可能把旧 100–119 一起返回。请求成功，消费者随后跳到 120，反而漏掉真正的 diskless 100–119。

补丁为远端 Fetch 增加排他的 upper bound，只返回完整且结束位置低于 seal 的 batch，aborted transaction 查询也使用同一上界。最终不仅在 phase 2 生效：评审指出 phase 1 中低于本地 log start 的读取同样会走远端，因此修订覆盖两阶段中所有已提交 seal 的前缀读取。[phase 1 漏洞与修订](https://github.com/aiven/inkless/pull/867#discussion_r4539195257) · [合并提交](https://github.com/aiven/inkless/commit/0e3aed895ea30d1dc6b896104b49118110bbdf56)

这不是“所有非干净选主后的 Tiered Storage 历史都已修好”。PR 明确把选主后又发生新 produce、分界不再等于 seal 的一般问题留在范围之外；人为把 seal 设置到 batch 内部时，整批裁剪可能返回空结果，最终增加告警帮助定位，而没有切开 batch。[边界告警评审](https://github.com/aiven/inkless/pull/867#discussion_r4548082755)

### 缺失 recorded epoch 的升级问题仍不能略过

#857 的正文仍以 0.50 没有 flag 发起端推断“没有已发布分区缺少 recorded epoch”，但上期已核验 **0.51 含 flag 发起端，且发布早于 #857 合并**。合并代码对缺失 `lastClassicLeaderEpoch` 的副本跳过新历史检查，重建也保留旧路径。本期没有核实到为这些既有 phase 2 分区自动补记该字段的升级方案，因此继续保留上期疑问，不能照抄 PR 的泛化结论。[0.51 发行说明](https://github.com/aiven/inkless/releases/tag/inkless-release-0.51) · [固定 ReplicaManager](https://github.com/aiven/inkless/blob/8ac5704ac8ac86be1c8f602b9a1383d94878df60/core/src/main/scala/kafka/server/ReplicaManager.scala)

## 3. ISR 与 epoch cache：两项修复都在评审中收紧了适用范围

### 高水位追齐只能依赖足够的历史证明

[#866](https://github.com/aiven/inkless/pull/866) 于 **11 月 12 日 09:06:34 UTC** 合并。它处理 follower 已到 seal、HW 却仍落后的停滞：最终一次 HW 更新没有被 follower 接受，而增量 Fetch session 已认为发送过，冻结的分区后续不再携带变化，消费者可能持续重试。

**最终代码比 PR 开场描述更窄：仅对 phase 1、仍在 ISR、LEO 已到 seal 的 follower 提升 HW；phase 2 或 ISR 外副本不走这个捷径。** 原因是 phase 1 的复制与 ISR 准入可以证明前缀已校验，而 phase 2 自动接纳活跃副本，成员身份本身不证明历史一致。评审因此撤回 phase 2 的直接 HW 恢复，保留 reconciliation fetch。[前缀校验质疑](https://github.com/aiven/inkless/pull/866#discussion_r4513997084) · [最终实现](https://github.com/aiven/inkless/blob/12d1e3cf09d8dd1fce3dc16401e292a743b6c4b3/core/src/main/scala/kafka/server/ReplicaManager.scala)

此外，人工评审指出正文时序把 seal 提交与 leader epoch 增加混在一起，要求覆盖 **seal 单独作为 delta 到达、leader epoch 不变**的路径。作者补测并报告 260 项该测试类测试通过；原始故障中响应被丢弃的具体时序仍有讨论，本期不把描述中的每一步当作已独立复现的因果链。该修复的可验证事实是收紧后的代码及新增测试，而非所有弱网场景已经关闭。[时序纠正](https://github.com/aiven/inkless/pull/866#issuecomment-6771377237) · [补测说明](https://github.com/aiven/inkless/pull/866#issuecomment-6794113487)

### 修复未来写入，还必须处理已经损坏的缓存

[#864](https://github.com/aiven/inkless/pull/864) 于 **11 月 11 日 11:29:33 UTC** 合并。经典 makeLeader 会为新 leader epoch 追加缓存项，而 consolidation 用较低、稳定的 diskless epoch 写入；非单调 epoch 赋值会清掉旧映射，使远端上传找不到 epoch、消费持续收到 `OFFSET_NOT_AVAILABLE`。即使 controller 没换 leader，broker 重启也可能走这条路径。

最初补丁只避免今后的错误赋值，11 月 10 日评审要求补上已有损坏数据的恢复。最终对 born-diskless 分区，在下一次 consolidated append 前恢复 `(epoch 0, log start offset)`；对已缓存较低 consolidation epoch 的 leader 跳过新的 epoch 项，但刚到 seal、尚无 diskless epoch 的副本仍需要临时项，不能无条件跳过。[恢复路径要求](https://github.com/aiven/inkless/pull/864#discussion_r4527474520) · [固定修订](https://github.com/aiven/inkless/commit/155da28965984fadcacb51533a6a166eaa7cdbce)

限制仍有实际运维意义：没有新 append 就不触发修复；已经以错误索引上传的 segment 不会因本地修复而自动重写；由 classic 迁移来的分区不能安全地重置为 epoch 0，仍需独立处理。故这项合并不等于旧集群所有 epoch/cache 问题已消除。

## 4. 时间戳查询的新候选：不再把未搜索的前缀当成不存在

上期 [#848](https://github.com/aiven/inkless/pull/848) 仍未合并，本周工作转向 **11 月 12 日提出的 [#870](https://github.com/aiven/inkless/pull/870)**。本期截止 **11 月 13 日 12:00 UTC 时它仍开放**。后续检索看到的合并时间为 **12:25:19 UTC**，不计本期合并或发布；以下按截止前最终候选 [f483f43a](https://github.com/aiven/inkless/commit/f483f43a399e12027a39e2a392d5a4a5f43a2064) 与回复说明。

原错误并不一定返回异常：本地重建中的副本查不到远端前缀，再去只知道 WAL 的控制平面查询，就可能给出更晚 offset，静默跳过仍保留的数据。新候选比较“可搜索的本地范围”与 WAL start / seal，覆盖不到时返回可重试错误；检查还绑定日志对象、truncation count 和 log start，防止异步查询过程中发生重建、替换或 retention，前后两次简单采样却错误地放行。[并发恢复质疑](https://github.com/aiven/inkless/pull/870#discussion_r4551052748) · [log start 变化修订](https://github.com/aiven/inkless/pull/870#discussion_r4551376075)

11 月 13 日评审又带来两类不同结果：

- phase 1 不进行 consolidation，若 DeleteRecords 已合法越过 seal，不能再用 WAL start 差距强制重试；作者 10:44 的修订将这项检查限制于 consolidation active，仍保留 seal 检查。控制平面响应增加分区匹配校验，epoch 批量恢复先完整验证再一次可见。[评审及回应](https://github.com/aiven/inkless/pull/870#discussion_r4562279662)
- **HW/LSO 仍落后时，LEO 不等于消费者可搜索上界**，评审认为这是既有问题，可另案处理。即使该候选合并，仍不能宣称 seek-by-time 所有跳数情形都解决。[明确留下的问题](https://github.com/aiven/inkless/pull/870#discussion_r4562279649)

11:03 新增 `ConsolidationDeferredListOffsetsRate`，使“副本不能恢复、所以一直返回可重试错误”的代价可观察。评审提出 #848 可由此关闭，作者把关闭动作留给维护者；截至窗口不将建议记成已经关闭。[指标与关闭建议](https://github.com/aiven/inkless/pull/870#discussion_r4562408122) · [作者回应](https://github.com/aiven/inkless/pull/870#discussion_r4562510630)

## 5. 人工恢复与测试：尚未合并的工作暴露更多边界

[#855](https://github.com/aiven/inkless/pull/855) 仍开放，当前候选 [99c145d4](https://github.com/aiven/inkless/commit/99c145d4772855f700b42bbce31c2151769b2a29) 比上期补了三个重要限制：恢复字段必须使用 RPC v1，否则旧 controller 会忽略新字段却返回成功；不能只凭 HW 认定 ISR 外副本保存正确历史；降 seal 若丢失事务 marker，必须说明其事务语义。候选以清空未决 producer state 让恢复继续，但文档明确承认 `read_committed` 可能收到新 seal 前原本未决事务的记录。这是灾难下有损恢复的取舍，绝不是恢复了原事务结果。[版本及事务评审](https://github.com/aiven/inkless/pull/855#discussion_r4512435171) · [事务边界](https://github.com/aiven/inkless/pull/855#discussion_r4512435246)

**11 月 12 日新开的 [#868](https://github.com/aiven/inkless/pull/868)** 将 WAL prune 的 keep offset 限制在 `highestOffsetInRemoteStorage + 1`，避免人工降 seal 后，清理把 WAL 起点直接跳到第一个剩余 batch，使远端重建结束点与 WAL 接续点之间无法推进。它是 #855 的前置修复，截止仍开放；不能把新 SQL migration V32 当成已发布 schema。

同日提出的 [#871](https://github.com/aiven/inkless/pull/871) 是文档与测试候选，纠正“phase 1 禁止 unclean election 就意味着只能等待原 ISR 回来”的绝对说法：启用 ELR 时，KIP-966 的 last-known-leader election 在普通选举类型判断之前执行，仍可能选出经历丢盘的最后 leader，broker 随后因 LEO 小于 seal 把分区标 offline。候选没有改变 controller 行为，而是解释有损恢复步骤及适用条件。其集群测试需人为控制上传 gate 与恢复顺序；这些是项目测试证据，不是本次生产验证。[#871 原文与测试](https://github.com/aiven/inkless/pull/871)

[#869](https://github.com/aiven/inkless/pull/869) 则承认旧 14 个 switch 系统测试只有 1 个启用 consolidation，很多测试根本没到 phase 2。候选把完成条件改为每个分区都看到 phase 2 flag，并核对已确认消息的 partition、offset、key、value。评审还要求不能接受重复 offset 覆盖账本，并使滚动重启**确实与阶段转换重叠**，而不只是先后都运行过。截止仍开放，不能将计划中的故障矩阵写成已经全面验收。[重叠性评审与修订](https://github.com/aiven/inkless/pull/869#discussion_r4550868827)
