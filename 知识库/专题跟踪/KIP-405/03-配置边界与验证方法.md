# KIP-405 配置边界与验证方法

理解实现后，部署问题可以化为三个问题：远端对象由谁可靠保存，哪些进度允许本地数据回收，故障时怎样证明读到的是正确历史。本文以 **3.9.0 的具体配置校验代码**为主；后续版本演进见[[知识库/专题跟踪/KIP-405/01-落地轨迹与设计演进|落地轨迹]]。这里给的是验证方案，没有声称已经跑过性能测试或生产演练。

## 1. 两层开关，两个不同的插件职责

broker 的 `remote.log.storage.system.enable` 打开功能基础设施；topic 的 `remote.storage.enable` 决定该 topic 是否参与分层。只改其中一个，不能得到完整可用的 tiered topic。

- `remote.log.storage.manager.class.name` / `.class.path`：加载 RemoteStorageManager，负责远端日志段与辅助文件的实际保存、读取、删除。
- `remote.log.metadata.manager.class.name` / `.class.path`：加载 RemoteLogMetadataManager，负责段位置、状态和生命周期的元数据。
- 默认 topic-based RLMM 使用内部 Kafka topic；需配置 `remote.log.metadata.manager.listener.name`，使内部客户端能够通过对应 listener 访问集群。

Apache Kafka 核心提供集成机制和默认元数据实现，**不附带开箱即用的生产 RemoteStorageManager**。官方 quick start 的 `LocalTieredStorage` 是测试实现，用本地目录模拟远端存储，不能凭这个例子宣称已经具备 S3 生产耐久性。[3.9 运维说明](https://kafka.apache.org/39/operations/tiered-storage/)

工程评估应把插件作为独立交付物检查：复制返回成功的耐久性含义、部分上传如何清理、重试幂等、range read、删除幂等、认证与加密、对象 key 布局、错误分类以及升级兼容性。Kafka 的元数据状态机不能补救一个“返回成功但未可靠保存文件”的插件。这是根据接口职责得到的工程推论，不能用 Kafka 的 GA 标签代替插件验收。

## 2. 保留期不是上传定时器

`segment.bytes` / `segment.ms` 控制日志滚动，后台复制选择已关闭并满足稳定性条件的段。`local.retention.ms` / `.bytes` 控制本地层的回收目标；它们不是“到这个时间才开始上传”的条件。即使本地还要留一天，段也可能早已上传，形成冷热两份重叠区间。对象上传完成也不意味着立即删除本地段，仍要满足本地回收条件。[复制路径](https://github.com/apache/kafka/blob/84caaa6e9da06435411510a81fa321d4f99c351f/core/src/main/java/kafka/log/remote/RemoteLogManager.java) · [本地日志与回收](https://github.com/apache/kafka/blob/84caaa6e9da06435411510a81fa321d4f99c351f/core/src/main/scala/kafka/log/UnifiedLog.scala)

| 配置 | 意义 | 容易犯的错 |
|---|---|---|
| `retention.ms` / `retention.bytes` | topic 总体保留策略，包含远端历史的生命周期 | 当成只约束本地盘，误以为对象存储永久保留 |
| `local.retention.ms` / `.bytes` | 本地层保留目标，按分区与日志段粒度生效 | 当成硬实时磁盘上限，忽略未完成上传和段滚动 |
| local 值 `-2` | 继承对应整体 retention | 当成无限保留；真正特殊值语义应分别核对 |
| 有限整体 retention | local 有效值不能大于整体值 | 只看配置能被解析，不检查组合校验 |

`LogConfig.localRetentionMs/Bytes` 实现了 `-2` 的继承；`validateRemoteStorageRetentionTime/Size` 检查本地与总体配置关系。`validateNoRemoteStorageForCompactedTopic` 拒绝 compacted topic。[3.9.0 LogConfig](https://github.com/apache/kafka/blob/84caaa6e9da06435411510a81fa321d4f99c351f/storage/src/main/java/org/apache/kafka/storage/internals/log/LogConfig.java)

> 例子只是帮助理解：整体保留 30 天、本地保留 6 小时，并不代表只有“刚满 6 小时”的段才上传。上传跟随滚动和稳定性；6 小时影响本地回收。长时间未完成的事务可能阻止稳定前沿推进，远端故障可能拖慢上传，所以磁盘预算必须留出积压余量。

## 3. 停复制、彻底关闭、关闭 broker 功能不是同一个操作

**3.9.0 KRaft 模式**的代码支持以下两种 topic 级转变：

| 目标 | 配置组合 | 结果/风险 |
|---|---|---|
| 保留远端历史可读，停止新上传 | `remote.storage.enable=true`，`remote.log.copy.disable=true` | 新写入更多依赖本地保留；远端数据仍受总体 retention 管理，不能理解为永久冻结 |
| 关闭分层并删除远端数据 | `remote.storage.enable=false`，`remote.log.delete.on.disable=true` | 远端独有历史会被删除；这是数据生命周期变更，不是无损回滚 |

停止复制后，`UnifiedLog` 使用整体 `retention.ms/bytes` 计算本地保留，并且回收不再以“已上传”作为门槛；local 配置不再构成独立的短保留窗口。停止复制时，local retention 必须设为 `-2` 或等于整体 retention。原因是此时不能继续按较短的本地保留窗口丢掉尚未上远端的数据。3.9.0 的 `validateRetentionConfigsWhenRemoteCopyDisabled` 明确校验这一组合；`validateTurningOffRemoteStorageWithDelete` 拒绝直接从开启变为关闭却不声明删除；`validateNoInvalidRemoteStorageConfigsInZK` 明确拒绝在 ZooKeeper 模式使用这两个新配置。[LogConfig 校验](https://github.com/apache/kafka/blob/84caaa6e9da06435411510a81fa321d4f99c351f/storage/src/main/java/org/apache/kafka/storage/internals/log/LogConfig.java)

broker 级关闭还有额外前提，不能把 topic 的停复制操作等同于关闭整个远端子系统。实施前应按所用版本的运维文档确认已有分层 topic 的处置与启动校验，而不是直接翻转 `remote.log.storage.system.enable`。[3.9 操作边界](https://kafka.apache.org/39/operations/tiered-storage/)

### 一个很具体的文档陷阱

3.9.0 `TopicConfig` 的 `REMOTE_LOG_STORAGE_ENABLE_DOC` 仍带有“启用后不能关闭”的旧说明，但同一文件已定义 copy-disable/delete-on-disable，`LogConfig` 已实现组合校验。因此不能只读生成配置文档的一句说明；需要联合发布公告、运维步骤和实际校验实现判断生效能力。[旧说明所在源码](https://github.com/apache/kafka/blob/84caaa6e9da06435411510a81fa321d4f99c351f/clients/src/main/java/org/apache/kafka/common/config/TopicConfig.java) · [实际校验实现](https://github.com/apache/kafka/blob/84caaa6e9da06435411510a81fa321d4f99c351f/storage/src/main/java/org/apache/kafka/storage/internals/log/LogConfig.java)

## 4. 用什么实验验证“真的落地”

建议在隔离测试集群用固定 Kafka 版本和固定插件版本执行，记录配置、段大小、数据分布、请求大小、并发、对象存储区域与费用。下面列的是可验证命题，不提供未经测量的百分比收益。

| 场景 | 注入/步骤 | 需要观察的证据 |
|---|---|---|
| 热读转冷读 | 写到多次滚段；等上传完成及本地回收，再从早期 offset 消费 | 记录逐条 offset/校验值连续；远端实际读取；消费者接口不变 |
| 未完成事务跨段 | 开事务、写过滚段边界、延迟 commit/abort | LSO 限制上传候选；完成后可继续上传；read_committed 消费者不向应用返回 aborted records（不等于 broker 从 Fetch 字节中剔除了这些记录） |
| 上传失败 | 在 STARTED 后、复制中或 FINISHED 前注入错误 | 失败段不被作为完成副本；本地回收没有跨过安全进度；重试与残留对象处理符合插件契约 |
| leader 切换 | 在复制/删除进行中切换 leader | 新 leader 按 epoch 与元数据重建进度；没有误读同 offset 的旧历史，也不把未完成状态当成功 |
| 新 follower bootstrap | 新副本加入；让期望 offset 已不在 leader 本地层 | 验证 epoch/producer snapshot 恢复与尾部追赶；注明 3.9 与 4.3 KIP-1023 模式的不同起点 |
| 远端删除中断 | 删除开始后中断进程并恢复 | DELETE_STARTED 不再作为正常可读候选；删除可重试，完成后元数据收敛 |
| 元数据可用性 | 中断元数据内部 topic 访问，但保持对象存储可用 | 不会仅凭对象存在就宣称段可读；观察元数据初始化、发布等待、超时与恢复 |
| 停复制/关闭 | 在测试 topic 执行两种配置组合 | 停复制仍能读远端历史；彻底关闭的删除后果与文档一致；非法组合被拒绝 |

验收应同时看正确性和服务质量：上传滞后、本地剩余容量、远端读延迟/队列、复制与读取错误、删除积压、元数据消费进度、索引缓存命中与对象请求量。只检查“对象桶里出现了文件”远远不够。生产告警阈值应根据实际负载和故障恢复窗口设定；本文不虚构通用阈值。

## 5. 收益与成本要按路径算

- **确实解耦了一部分容量**：长期历史不必一直留在每个 broker 本地副本上；新副本不必把全部冷历史再复制一遍。
- **没有消除热路径复制**：新写入仍走分区 leader、本地日志和副本协议，后台才把稳定关闭的段移入远端。
- **冷读转移了瓶颈**：远端请求延迟、请求费、网络吞吐、反序列化和索引缓存成为新变量，不能拿热读 page-cache 延迟外推。
- **段大小形成取舍**：较小段可能更早卸载，但提高对象/索引/元数据操作频率；较大段减少对象数，却拉长滚动和进入远端的等待。事务稳定性还会加入另一层等待。
- **对象耐久性不等于备份完整性**：还需要元数据、topic 身份/epoch、插件配置与凭证，以及经过验证的恢复路径。不要把单个 bucket 当成可直接替代 Kafka 全集群备份的自描述文件夹。

这些是从实现责任划分推导出的工程判断，收益幅度需要自己的测试。与[[知识库/专题跟踪/KIP-1150/README|KIP-1150 Diskless]]对照时尤其要保留边界：KIP-405 改造历史段的长期存储；Diskless 进一步讨论新写入的持久化与接入路径，不能只因为两者都使用对象存储就认定等价。
