# 读路径优化的四种边界：格式、进度、介质与调度

本期材料可分成两层问题：先证明替换后的读路径仍能给出约定的结果，再判断工作量转移是否值得。这是跨案例的工程归纳，不是四个系统共享的协议，也不增加独立实验证据。

## 第一层：哪些读路径可以替换

[[知识库/wiki/虚拟Parquet-固定布局与按需转码]] 和 [[知识库/wiki/流湖交接-快照进度与Freshness边界]] 都在既有读者与新的数据位置之间增加中介，但前者必须履行字节布局/范围读取契约，后者必须履行逐 bucket 的可见进度契约。格式能被解析，不能证明行集拼接没有遗漏、重复或错误处理删除；快照进度正确，也不能证明虚拟文件的偏移可以预先计算。

因此不能把“兼容 Parquet”和“统一流湖表”合成一个笼统的兼容性结论。[[知识库/wiki/数据湖-提交结果不确定性与有界重试]] 提供第三个不同约束：提交结果不确定时，重试是否仍然安全。成功读到文件不能回答此前写入是否已提交。

已有 [[知识库/wiki/Fluss-Tiering分层架构]] 给出先提交快照、后报告进度的顺序，[[知识库/wiki/Fluss-Lake层与湖仓融合]] 说明插件和转换职责。本期补充说明：仅有这个顺序仍不足以构成延迟 SLA，还要核对逐 bucket 停止位置、旧尝试 epoch 和首轮主键快照。将这些条件分开，才能判断是可见性错误，还是本轮尚未处理到目标位置。

## 第二层：减少的工作是否是主要成本

[[知识库/wiki/纠删恢复-读取量与寻道共同优化]] 与 [[知识库/wiki/SWA缓存-有界重算与图捕获开销]] 揭示相同的测量陷阱：总量更小，不保证执行更快。前者需同时考虑读取字节和寻道形状；后者需同时考虑重算 token 与 kernel 启动开销。两者都要求记录工作如何被分割，而不是只看总量。不过 HDD 寻道与 GPU 调度是不同机制，不能互换系数或性能倍数。

[[知识库/wiki/LSM-Tree-硬件适配]] 中“介质改变成本模型”的视角可以迁移到 LESS 的评估方法，但 LESS 不是 LSM 算法；HDD 恢复收益不能证明 NVMe 收益或写放大改善。同样，[[知识库/wiki/KV缓存-路由索引缺口与有限重放]] 的有界补账修复路由状态，SWA 重算恢复模型窗口状态；前者的序号连续性不证明后者的数值等价或质量无损。

这也反过来约束第一层：虚拟 Parquet 将存储/兼容问题转为转码 CPU 和网络字节；流湖交接把可见延迟分散到轮次、排队、快照提交与进度登记。中间量是诊断线索，不是最终收益。

## 可复用的评估顺序

1. 固定结果契约：明确读者布局、行集和删除语义、提交状态，以及模型允许的质量差异。先设计违约场景，再测吞吐。
2. 固定适用条件：记录版本、数据分布、介质、网络、batch、缓存开关和首次/后续轮次；不能把不同实验的数据拼成一项收益。
3. 拆开工作总量与执行形状：分别测转码 CPU/返回字节、各阶段可见时刻、恢复字节/寻道、重算 token/启动次数，再观察端到端尾延迟或质量。
4. 对照代价是否外移：检查写入和编码成本、并发服务能力、错误恢复及未覆盖工作负载。局部优化只有在目标环境中端到端收益成立，才值得推广。
