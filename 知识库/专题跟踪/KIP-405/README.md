# KIP-405 从提案到生产落地

**KIP-405（Kafka Tiered Storage）已经落地。** 但它经历了两个不同的交付关口：Kafka **3.6.0（2023-10-10）**首次 Early Access；**3.9.0（2024-11-06）**官方宣布 production-ready。此后仍继续完善性能、恢复和运维行为，不能用“已实现”抹掉这些阶段。[3.6 公告](https://kafka.apache.org/blog/2023/10/10/apache-kafka-3.6.0-release-announcement/) · [3.9 公告](https://kafka.apache.org/blog/2024/11/06/apache-kafka-3.9.0-release-announcement/)

## 抓住一条主线

KIP-405 把**已关闭并满足稳定性条件的日志段**转移到远端存储，同时让消费者继续用 Kafka 的 offset 和 Fetch 协议读取历史。它的难点不在上传一个文件，而在以下几件事必须一起成立：

- 文件上传成功前，不能误当成可读的远端副本。
- 本地删掉一段后，索引、事务判断和恢复状态仍要够用。
- leader 换届后，不能仅凭 offset 误认旧历史；元数据必须携带 epoch 与身份。
- 远端读取不能把慢 I/O 堵在普通请求处理线程上。
- 过期/禁用/删除发生中断后，数据面与元数据面需要继续收敛。

因此它最终形成的是一套日志生命周期协议：**本地热写与复制 + 后台段级复制 + 强一致元数据接口 + 远端按需读取 + 可恢复删除状态机**。这里“关键流程”主要指跨组件交互；Kafka transaction 的 commit/abort 和 read_committed 则在源码篇中单独讨论，避免混成同一个概念。
