# KIP-1150 周记：ISR 语义与迁移边界推进

观察区间：**2026-10-09 12:30:00 至 2026-10-16 12:16:39 UTC**。检索截止为本期实际核验时间，北京时间 10 月 16 日 20:16:39。事件按原始邮件 Date、Confluence 版本时间及 GitHub merged_at 记录。

本周有实质设计进展：**KIP-1163 把 Diskless 副本和 classic 耐久副本的职责分开，并补写 classic / diskless 迁移的封印边界。**进展仍停留在讨论稿；1150 的 Accepted 没有变成子 KIP 已通过、上游已合并或正式发布。背景见[[知识库/专题跟踪/KIP-1150/2026-10-09-从起点到现在|首篇]]。

### 1. ISR 回到数据完整性的职责

上期 v23 仍要求副本向 leader 发空 Fetch 来跟踪 ISR，并把 Diskless 的 in-sync 理解为追上协调器。v24 删除了这段描述，明确 **Diskless 副本不进入分区 ISR**：对象存储已经承担其 payload 耐久性，本地副本主要服务缓存和请求放置。纯 Diskless 分区可以健康地拥有空 ISR；Hybrid 分区尚有 classic 日志时，ISR 仍标识承担那部分耐久性的副本。

副本重分配也随之分开：纯 Diskless 的新增/移除副本，在节点确认分配后退出 AddingReplicas / RemovingReplicas，不沿用“先追入 ISR 才能退出”的条件；Hybrid 则仍需新副本进入 ISR 后再移走旧副本。这里变化的是**提议的状态机与安全前提**，不能据此把现有 Kafka 集群的空 ISR 告警直接关掉。[1163 v24](https://cwiki.apache.org/confluence/rest/api/content/350783976?status=historical&version=24&expand=version,body.storage)

技术意义：草案开始将“负责保存唯一耐久数据”与“有缓存、适合服务请求”分开表示。这样可以减少仅为缓存预热等待 ISR 的约束，但健康状态不等于缓存已热；尾延迟、远端读取压力和请求路由还需另行定义和验证。这是本文的工程解读，不是已测性能收益。

### 2. 迁移开始有明确的写入接管边界

v24 新增四个分区状态：CLASSIC、DISKLESS，以及迁移期间分别继续接收 classic 写入或 diskless 写入的 HYBRID_CLASSIC、HYBRID_DISKLESS。旧数据不会因为切换开关立即转换；需要 retention 或上传 Tiered Storage 后逐步收敛。v25 进一步补充 classic→diskless 的写入接管：通过原子变更 StorageEngines 并提升 leader epoch，发起 classic log 封印及旧 leader 隔离；Diskless Coordinator 等 classic 复制完全追齐后，才接受新的 produce。[v24 正文](https://cwiki.apache.org/confluence/rest/api/content/350783976?status=historical&version=24&expand=version,body.storage) · [v25 修订记录](https://cwiki.apache.org/confluence/rest/experimental/content/350783976/version/25) · [当前正文](https://cwiki.apache.org/confluence/spaces/KAFKA/pages/350783976/KIP-1163+Diskless+Core)

例如，假设一次切换前已有一段 classic 历史数据：切换解决的是后续写入由谁接管，历史数据的耐久责任不会凭空转移。等 classic 前缀真正分层或过期之后，才能消除它对本地耐久副本的依赖。这个例子说明了为什么新写入已走对象存储，分区仍可能需要 Hybrid 状态及 ISR。

v25 的价值是开始交代“旧写入何时停止、新写入何时开始”，而不只是增加一个配置开关。它还没有给出已验证的完整故障协议；classic→diskless、反向切换、重复切换与中途故障的闭环仍需明确。

## 对上一轮异议，回应到哪一步

对照 [Jun 7 月 20 日的跟进](https://lists.apache.org/thread/y32byddj88wrj0f8j2n4r49kz97yqc52)，本期可以把问题推进状态拆开记录：

- **JR3：ISR/ELR 还没有落实到正文。** 1163 现在确实改写了 ISR 与分区状态，属于实质回应；这不等于所有选举、ELR、客户端展示与监控语义已完备。
- **JR4：没有跨 broker 数据复制，为何还发空 Fetch？** 旧的空 Fetch 描述已经删除。但删除旧段落不能证明协调器缓存提示和完整替代协议已设计好；当前 Consume path 段仍保留优先选择同 rack 的 ISR 副本、仅在没有这类副本时才选择 non-ISR 的表述，需与新语义一起澄清。
- **JR5：对象存储恢复与 classic 重分配不是同一流程。** 新稿分别描述纯 Diskless 与 Hybrid 的加入/移除条件，回应更具体；缓存冷启动和异常恢复仍需测试证据。
- **JR6.2：幂等、producer state 和 aborted index。** 本期未闭合。1163 仍把具体幂等与事务细节留给另一个 KIP；1165 仍将事务列为后续工作。

以上为正文和邮件的对照分析。检索范围内未发现评审者在这次修改后确认全部异议已经解决，也未发现 1163/1164/1165 的新投票或接受结果。

## 子 KIP 之间仍需对齐

截至截止点，1150 仍为 v20（3 月 2 日）、1164 仍为 v24（9 月 30 日）、1165 仍为 v21（10 月 2 日）；只有 1163 推进到 v25。1150 为 Accepted；1163、1164 为 Under Discussion；1165 为 Under Discussion (Re-Opened)。

新旧正文不能拼成一份已经一致的规范：

1. **迁移范围不同。** 1150 把 Topic Type Changing 列为后续工作，1163 已提出动态双向迁移，1165 的 `diskless.enable` 仍写 create-time only。
2. **对象整理路线不同。** 1163 仍保留 WAL-object merging 并指向 1165；1165 明确排除这条 merging 路线，改为 WAL 重建经典单分区 segment，再交给 KIP-405。
3. **最小依赖集合不同。** 1165 提议自己成为从创建起必需的 consolidation 依赖；1150 已接受正文仍列 1163、1164。

这些是当前草案之间可直接核对的差异，并不能据此认定较新的某一段已经取代其他提案。下一步需要作者将范围、术语和协议边界统一，再进入各自表决。[1150](https://cwiki.apache.org/confluence/spaces/KAFKA/pages/345377898/KIP-1150+Diskless+Topics) · [1163](https://cwiki.apache.org/confluence/spaces/KAFKA/pages/350783976/KIP-1163+Diskless+Core) · [1165](https://cwiki.apache.org/confluence/spaces/KAFKA/pages/350783996/KIP-1165+Object+Consolidation+for+Diskless)

另一个较小但可检查的信号：1163 新增的 AlterPartitionRequest、PartitionRecord / PartitionChangeRecord 示例，注释已写新增版本，`validVersions` 仍保留旧范围。它说明协议样例还需校整，不能把 KIP 中的 JSON 当作已进入上游且可生成代码的协议文件。

## 下一观察点与检索边界

1. 1163 是否补齐 Hybrid 切换失败、反向/重复迁移、ISR/ELR 与客户端路由的统一规则，并与 1165 create-time 配置对齐。

3. 子 KIP 是否进入正式投票；是否出现可关联的上游实施 PR、故障测试与明确发布版本。独立 fork 的部分合并另行跟踪。
